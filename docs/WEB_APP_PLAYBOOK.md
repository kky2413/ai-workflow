# 웹사이트·업무 서비스 개발 실전 절차

목표는 예쁜 데모 화면이 아니라 **실제 사용자의 입력이 처리·저장되고 결과가 화면에 반영되는 서비스**입니다.

## 1. 먼저 요구사항을 구체화

- **사용자:** 누가 어떤 문제를 해결하는가? 가장 중요한 화면과 사용자 행동 1~3개는?
- **데이터:** 입력 파일/DB/API, 열·식별자, 시간·단위, 유효 범위, 저장 수명은?
- **출력:** 필수 화면, 서버 API, 내보내기 형식, 제출 위치와 실행 명령은?
- **기존 코드:** README → package.json scripts → 진입점 → 라우트 → 서버 → 저장소를 따라갑니다.
- **불확실성:** 요금·배차·권한·계산식 등 결과를 바꾸는 업무 규칙은 추측하지 않습니다.
- **완료 조건:** 필수 요구사항 하나에 검증할 실제 사용자 동작 하나를 연결합니다.

## 2. 기존 기술을 유지

| 프로젝트 | 우선 살펴볼 부분 | 흔한 실수 |
| --- | --- | --- |
| Vite + React/Vue | src, 구성 요소, API 호출, package.json | UI 작업 때문에 전체 재설치 |
| Next.js | app 또는 pages, 서버/클라이언트 경계, API, 인증 | 비밀 값을 클라이언트에 노출 |
| Node/Express | 라우트, 미들웨어, 서버 엔트리, 저장소 | 상태 코드·입력 검증 누락 |
| Flask/FastAPI | 라우트, 의존성, 테스트, 데이터 흐름 | 없는 패키지를 무리하게 설치 |
| 빈 폴더 | 제공된 런타임, 제출 조건, 최소 기술 조합 | 예제 앱을 그대로 제출물로 사용 |

새 Vite 프로젝트를 꼭 만들어야 할 때만 공식 Node 호환 버전·설치 정책을 확인합니다. **Node 22 이상이라고 해도 기존 프로젝트의 실제 의존성 확인은 필요합니다.**

## 3. 기능 하나를 끝까지 (Vertical Slice)

~~~text
사용자 클릭·입력
   → 프론트의 요청·입력 상태
   → 실제 서버 API
   → 서버 검증·업무 계산
   → 데이터 저장 또는 결과 생성
   → HTTP 성공·실패 응답
   → 화면 갱신과 오류 메시지
   → 다시 조회·새로고침으로 확인
~~~

필수 입력/조회 → 핵심 처리·저장 → 수정/삭제·상태 변경 → 오류 처리 → 검색·정렬 → 시각 완성도 순서로 진행합니다. 하드코딩된 정답·가짜 성공 메시지는 완성 기능이 아닙니다.

## 4. 웹 UI의 완성도를 높이는 기준

- 주요 목표·제목·입력 라벨·단위를 선명하게 표시합니다.
- 로딩/빈 목록/오류/성공과 중복 클릭에 대한 피드백을 제공합니다.
- 데스크톱과 모바일에서 표·입력·버튼이 잘리지 않는지 확인합니다.
- Tab·Enter·Escape 등 기본 키보드 흐름과 명확한 포커스 표시를 확인합니다.
- 사용자 텍스트를 HTML 문자열로 합쳐 출력하지 말고 안전하게 표시합니다.
- 기존 앱의 디자인과 브랜드를 우선하고, 무관한 템플릿 장식은 줄입니다.

## 5. API·저장·핵심 알고리즘

- API마다 경로·메서드·필수 요청 필드·정상 응답·오류 응답을 기록합니다.
- 프론트 검증뿐 아니라 **서버에서도** 잘못된 입력·권한·범위를 검증합니다.
- 저장이 필수라면 변경 후 재조회·새로고침·서버 재시작 시 결과를 확인합니다.
- 실제 과제가 스케줄링·배정·최적화라면 UI와 분리해 **제약 조건, 목적 함수, 결과 유효성**을 검사합니다. 사이트가 열렸다고 결과가 맞는 것은 아닙니다.
- 비밀키·원본 업무 자료를 프론트 코드, 공개 저장소, 외부 서비스로 전송하지 않습니다.

## 6. 서버 실행과 Browser 미리보기 연결

**웹사이트 파일을 만들었다고 자동으로 미리보기가 열리지는 않습니다.** 실제 프로젝트의 개발 서버가 실행 중이어야 합니다. 플랫폼이 제공하는 Browser 미리보기 기능만 사용합니다.

1. **실제 프로젝트 루트 확인:** 터미널에서 `pwd` 또는 `Get-Location`, `ls` 또는 `Get-ChildItem`을 실행합니다. `README.md`와 `package.json`의 `scripts`를 읽고 실행 명령을 확인합니다. Codex 대화창과 **서버 실행 터미널은 구분**합니다.
2. **서버 시작:** 프로젝트에서 제공한 명령을 사용합니다. 예를 들어 Vite에서 `dev` 스크립트가 정의되어 있고 환경에서 허용하면 `npm run dev -- --host 0.0.0.0`을 사용할 수 있습니다. Next.js, Express, Flask 등은 **각 프로젝트의 실제 실행 명령**을 따릅니다. 필요하지 않은 새 프로젝트 생성·재설치·외부 배포는 하지 않습니다.
3. **포트 번호 확인:** 터미널의 `Local: http://localhost:5173/` 같은 메시지나 실제 서버 로그를 확인합니다. **5173은 예시**이며 3000, 8000 등 실제로 리슨 중인 포트와 다를 수 있습니다. 실행 중인 서버 터미널은 **종료하지 않습니다**.
4. **미리보기 연결:** 플랫폼 왼쪽 **Browser(지구본) 미리보기**에서 `PORT`에 **실제 서버 포트**, `URL`에 우선 `/`를 입력하고 새로고침합니다. 프로젝트의 진입 경로가 다르면 실제 라우트(예: `/dashboard`)로 바꿉니다. 자동 생성된 미리보기 주소를 외부에 공개할 필요는 없습니다.
5. **화면 확인:** 제목·입력·버튼을 확인하고 실제로 입력 → 저장 → 재조회 → 새로고침을 수행합니다. 서버가 켜진 것과 기능이 정확한 것은 **별개**입니다.

### 사진처럼 “포트 3000에 응답하는 서버가 없어요”가 나타나면

| 점검 | 해결 방향 |
| --- | --- |
| 서버가 실행되지 않음 | 실제 프로젝트 루트에서 README/package.json에 정의된 실행 명령을 시작하고 오류 로그 확인 |
| 서버가 5173 등 다른 포트를 사용 | Browser의 `PORT`를 **서버가 실제 표시한 포트**로 변경 |
| 서버가 켜졌다가 종료됨 | 서버 터미널의 마지막 오류를 확인하고, 장시간 실행 상태 유지 |
| 서버는 살아 있는데 플랫폼에서 접속 불가 | 정책상 허용되는 경우만 서버의 HOST 바인딩(예: `0.0.0.0`) 확인; 프록시·포트 경로는 플랫폼 안내에 따름 |
| 연결은 됐지만 빈 화면/404 | `URL` 경로, 프론트 콘솔·서버 로그, 정적 파일/라우팅 확인 |

**Codex에 바로 요청하는 문장:**

> 현재 실제 웹 프로젝트의 README와 package.json을 확인하고, 기존 스택에 맞는 개발 서버를 실제 실행해 주세요. 서버가 정상적으로 듣고 있는 HOST·PORT와 진입 URL을 로그로 확인하고, 플랫폼 Browser 미리보기의 PORT와 URL에 무엇을 넣을지 알려주세요. 서버 터미널을 유지해 주세요. 접속 오류가 있으면 실제 로그를 보고 원인을 구분하되, 허용되지 않은 설치·배포·외부 연결이나 보안 설정 우회는 하지 마세요.

**주의:** `0.0.0.0`은 서버를 모든 네트워크 인터페이스에 바인딩하므로, **플랫폼에서 미리보기용으로 허용한 경우에만** 사용합니다. 개인 PC에서는 필요 없다면 `127.0.0.1`을 우선합니다.

## 7. 장애 발생 시 빠른 구분

| 현상 | 먼저 확인 |
| --- | --- |
| 서버가 안 켜짐 | package.json 스크립트, 로그, 의존성, 포트 충돌 |
| 로컬은 되지만 플랫폼 미리보기는 안 됨 | 허용된 HOST 0.0.0.0, 포트·실제 미리보기 경로 |
| 빈 화면 | 브라우저 콘솔, JS 로딩, 렌더링 예외 |
| 버튼 눌렀지만 데이터 그대로 | 이벤트 → 요청 → 서버 → 저장 → 다시 조회 |
| 새로고침 후 사라짐 | 메모리 상태인지 실제 저장소인지 |
| HTTP 200이지만 값 틀림 | JSON 필드명, 계산식, 업무 단위, 독립 기대값 |

버그는 **재현 → 원인 하나 좁히기 → 최소 수정 → 같은 테스트 재실행 → 관련 기존 동작 확인** 순서로 해결합니다.

## 8. 마지막 제출 확인

실제 필수 기능마다 근거가 있는지, 직접 UI를 조작했는지, 실패/미검증을 정직하게 구분했는지, 더미·비밀값·불필요한 참고 파일이 제출물에 들어가지 않았는지 확인합니다.
