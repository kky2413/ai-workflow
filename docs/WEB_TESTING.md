# 웹사이트 검증 — API와 실제 화면은 별개입니다

사이트가 열리는 것만으로 요구 기능이 맞다는 뜻은 아닙니다. **요구사항 → 실제 사용자 행동 → 기대 결과 → 관찰 결과**로 확인합니다.

## 1. 프로젝트의 기존 검증 명령을 우선 사용

package.json의 `scripts`와 README를 확인합니다. 프로젝트에 `test`·`build`가 실제로 정의되어 있을 때만 해당 명령을 실행합니다. Python 프로젝트라면 준비된 테스트를 사용하세요.

## 2. 로컬 API 검증 (Python이 이미 있을 때)

선택형 도구 `scripts/web_api_check.py`는 **loopback HTTP**에서 상태 코드와 JSON 내용을 확인합니다. 기존 과제의 실제 API에 맞춰 설정 JSON을 작성해야 합니다.

~~~json
{
  "base_url": "http://127.0.0.1:3000",
  "cases": [
    {"name": "health", "method": "GET", "path": "/api/health", "expect_status": 200, "expect_json": {"status": "ok"}},
    {"name": "list", "method": "GET", "path": "/api/items", "expect_status": 200, "expect_json_fields": ["items"]}
  ]
}
~~~

~~~sh
python3 scripts/web_api_check.py --config /실제/검사설정.json
~~~

위 값과 경로는 **형식 예시**이지 실제 과제의 정답이나 필수 API가 아닙니다. 서버가 이미 실행 중일 때만 검증합니다.

- 외부 URL·프록시·리다이렉트 추적을 차단합니다.
- 기본은 GET/HEAD만 허용합니다. **실제 데이터 변경 가능성이 있는 POST·PUT·PATCH·DELETE는 --allow-writes가 필요**합니다.
- 빈 검사 목록, 실패와 실행 오류를 구분합니다.
- **HTTP·JSON 검사만으로 업무 계산·실제 UI 사용성을 증명하지 않습니다.**

## 3. 사용자가 직접 브라우저에서 확인

| 행동 | 기대 결과 |
| --- | --- |
| 실제 포트·경로 열기 | 페이지의 주요 콘텐츠·입력 보임 |
| 필수 버튼·폼 작동 | 실제 처리/저장 후 화면에 반영 |
| 값 수정·삭제·재조회 | 요청한 값만 변경, 다른 값 보존 |
| 새로고침 또는 서버 재시작 | 필요한 경우 저장한 상태 유지 |
| 빈 입력·유효하지 않은 입력 | 정의된 오류 처리와 안내 |
| 모바일 폭·키보드 | 잘림 없이 주요 입력 가능 |
| 서버 장애 | 가짜 성공 표시 없이 오류 안내 |

플랫폼의 브라우저 미리보기는 **사람이 직접 조작**합니다. 자동 브라우저 조작 도구는 해당 환경에서 명시적으로 허용된 경우에만 사용하세요. 직접 실행하지 않은 화면 테스트는 미검증입니다.

## 4. 제출 전

요구사항별로 실행 명령, 기대값, 실제 관찰값, 통과/실패/미검증 상태를 기록합니다. 마지막 검사 후 코드를 변경했다면 해당 기능을 재검증합니다. 최종 파일명·경로·필수 형식과 실제 출력까지 확인하세요.
